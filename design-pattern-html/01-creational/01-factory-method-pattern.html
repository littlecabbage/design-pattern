01

直觉认知：从“手工捏 Agent”到“标准化工厂”

在软件设计中，任何模式的诞生都不是为了凭空增加复杂度，而是为了解决现实业务演进中的代码腐化与紧密耦合。

💡

什么是 GoF 设计模式？

GoF (Gang of Four) 总结了 23 种经典的面向对象设计模式，其中工厂方法 (Factory Method Pattern) 属于创建型模式 (Creational Pattern)，专门用于优雅地解决“对象的实例化与组装”问题。

业务场景：我们要开发一个多智能体调度平台 (Multi-Agent Swarm)

假设平台需要动态调度三种不同的智能体：

  • CodeAgent (代码智能体)：配置 Claude 3.7 / GPT-4o 模型，绑定代码执行器 REPL 环境，需要初始化语法树解析上下文。
  • ResearchAgent (研报智能体)：配置长文本检索模型，挂载搜索引擎与 RAG 知识库。
  • DataAnalystAgent (数据分析智能体)：配置 Python Pandas/DuckDB 运行沙箱，挂载可视化图表生成器。

❌ 初学者的朴素写法（反模式：硬编码与高耦合）

如果直接在业务逻辑（客户端）中通过大量 if-elif-else 手工 new 实例，会发生什么？

🐍 Python · 糟糕的硬编码实现 (Anti-Pattern) 
# ❌ 错误示范：把所有 Agent 的繁琐构建逻辑全部塞在业务调度中心
class AgentDispatcher:
    def dispatch_task(self, agent_type: str, task_prompt: str):
        # 痛点 1：业务逻辑与具体的 Agent 创建细节强耦合
        # 痛点 2：每次新增一种 Agent，都必须打开这个核心文件修改 if-else
        if agent_type == "code":
            # 初始化 REPL 工具、加载 system prompt、配置 API Key、设定上下文窗口...
            agent = CodeAgent(model="gpt-4o", sandbox_port=8080, timeout=30)
        elif agent_type == "research":
            # 初始化向量数据库、配置搜索引擎 API、加载研报模板...
            agent = ResearchAgent(model="gemini-1.5-pro", vector_db="milvus", top_k=5)
        elif agent_type == "data":
            # 初始化 DuckDB 连接、注入 Pandas 上下文...
            agent = DataAnalystAgent(model="claude-3-7-sonnet", enable_charts=True)
        else:
            raise ValueError(f"Unknown agent type: {agent_type}")
            
        return agent.execute(task_prompt)
⚠️

这种写法为什么危险？

1. 违反 OCP (开闭原则)：明天新增一个 VisionAgent (视觉智能体)，你必须去修改核心调度类的源码，极易引发回归 Bug！
2. 违反 SRP (单一职责原则)：调度中心既要负责“任务分发”，又要精通每种 Agent 极其复杂的“装配细节”。

✨

工厂方法模式的核心解法

“定义一个用于创建对象的接口，让子类决定实例化哪一个类。”
既然每种 Agent 的装配逻辑各不相同，我们就为每种 Agent 配备一个专属的独立工厂（如 CodeAgentFactory、ResearchAgentFactory），将创建过程多态化！

UML 极简入门：看懂软件架构图的设计语言

在学习设计模式前，必须掌握工程师通用的交流蓝图—— UML (统一建模语言)。 我们只需掌握类图的 3 层结构与3 种关键连线即可！

📐 1. 类图 (Class Diagram) 的“三段式”矩形框结构

<<interface>>
Agent
+ name: String
- modelId: String
+ execute(task: String): Result
# initTools(): void

第一层 (类名区)：标明名称。若为斜体字或带有 <<interface>>，表示抽象类或接口。

第二层 (属性区)：格式为 可见性 属性名: 类型。

第三层 (方法区)：格式为 可见性 方法名(参数列表): 返回值类型。

可见性符号说明： + Public (公开)  |  - Private (私有)  |  # Protected (受保护)

🔗 2. 设计模式中最关键的 3 种 UML 关系连线用法

很多初学者分不清箭头含义。请记住：三角形代表继承/实现，普通箭头代表使用/依赖；实线代表强绑定，虚线代表抽象或临时关联。

03

工厂方法模式的四大核心角色 (角色拆解)

工厂方法模式之所以能实现解耦，是因为它将系统的对象结构严谨地拆分为“生产线”与“产品”两大层级，共包含 4 个角色：

1. 抽象产品 Abstract Product

Agent (智能体接口)

定义所有具体智能体必须遵守的业务操作协议（如 execute_task()、add_memory()），业务客户端只认这个抽象接口。

🎭 比喻：标准汽车规范，规定所有车都必须能“挂挡、前进、刹车”。
2. 具体产品 Concrete Product

CodeAgent / ResearchAgent

真正实现业务逻辑的具体智能体类，内部封装了各自不同的提示词策略、大模型调用参数和专属工具链。

🚗 比喻：奔驰越野车、特斯拉电动车，它们各自有不同的引擎构造。
3. 抽象工厂 Abstract Creator

AgentFactory (抽象智能体工坊)

声明核心的工厂方法 (Factory Method) create_agent() -> Agent，返回一个抽象产品。还可以包含通用的流水线前置校验逻辑。

🏭 比喻：总造车厂的设计图纸，规定每个分厂必须有一个“出厂验收装配线”。
4. 具体工厂 Concrete Creator

CodeAgentFactory / ResearchAgentFactory

覆盖（Override）父类的工厂方法，编写专属的装配代码，负责实例化对应的具体 Agent 对象并返回。

🔧 比喻：上海超级工厂负责组装 Model Y，斯图加特工厂负责组装保时捷。
💡

必背高频疑点：工厂方法里的「抽象工厂基类 (Abstract Creator)」≠「抽象工厂模式 (Abstract Factory)」

很多初学者看到代码里写了 class AgentFactory(ABC)（一个抽象的工厂基类），就误以为这是抽象工厂模式。 其实本案例是 100% 纯粹的「工厂方法模式 (Factory Method)」！

对比维度 本案例：工厂方法模式 (Factory Method) 进阶：抽象工厂模式 (Abstract Factory)
产品维度 单产品等级结构（只生产 1 种产品：Agent） 多产品族 / 产品全家桶（同时生产 LLMBrain + Memory + Sandbox）
工厂内方法数 只有 1 个工厂方法：create_agent() 有多个配套工厂方法：create_brain(), create_memory()
大白话通俗比喻 「专业代工厂只造车」：上海工厂造特斯拉 Model Y，斯图加特造保时捷。 「生态全家桶工厂」：苹果工厂同时生产 iPhone + Mac + Watch 一整套生态。

💡 时序图关键语法解析：
  • 生命线 (Lifeline)：垂直虚线，代表对象在系统运行周期中的存在时间。
  • 激活条 (Activation Bar)：生命线上的长方形细条，表示该对象正在占用 CPU / 正在执行方法。

05

深入反思：设计原则与适用边界

没有银弹！一个优秀架构师的标志不仅在于知道怎么用模式，更在于知道为什么用以及什么时候不该用。

🌟 工厂方法模式完美践行的三大设计原则：

1. 开闭原则 (OCP)

如果下周要新增一个 VisionAgent (多模态视觉智能体)，我们只需新增两个文件：VisionAgent.py 与 VisionAgentFactory.py。现有的核心代码一行都不用改！

2. 单一职责原则 (SRP)

CodeAgentFactory 只负责装配代码智能体，ResearchAgentFactory 只负责配置向量检索。职责边界清晰，修改不互相污染。

3. 依赖倒置原则 (DIP)

DIP (依赖倒置原则)：调度系统只依赖 Agent 和 AgentFactory 抽象，实现了“面向接口编程”。

✅ 核心优点 (Pros)

  • 解耦创建细节：避免高层业务模块充斥繁琐的实例化胶水代码。
  • 符合开闭原则：添加新智能体无需改动旧代码，架构扩展性极强。
  • 易于单元测试：可以轻松实现 Mock 工厂，向系统注入模拟的 Agent 进行自动化测试。

⚠️ 潜在代价 (Cons)

  • 类爆炸 (Class Proliferation)：每增加一个具体产品，就必须配套编写一个具体工厂类，增加了系统的类文件总数。
  • 代码间接层：对于极度简单、构造参数只有 1 个的对象，强行引入工厂方法会造成过度设计。

附录：初学者概念大白话速查字典

全篇概念通俗比喻总览（「xxx是xxx，如果你不理解，你就理解为xxx」）

📐 抽象类 (Abstract Class)
抽象类是包含规范但未完全完工的基类。如果你不理解，你就理解为：一张盖了公章的「半成品汽车设计图纸」——规定了车必须有方向盘和刹车，但不能直接当真车开上路。
🔌 接口 (Interface)
接口是纯粹的方法协议。如果你不理解，你就理解为：「墙上的国标五孔插座标准」——强制规定插头尺寸，不管你后面连的是电视还是电饭煲都能通电。
🚗 具体类 / 具体产品 (Concrete Product)
具体类是拥有所有零部件的实体。如果你不理解，你就理解为：「真正出厂能跑的特斯拉真车」——装配好所有零件，踩油门就能跑。
🎭 多态 (Polymorphism)
多态是同一调用在不同子类上有不同表现。如果你不理解，你就理解为：「老师喊一声开始做作业」——数学课代表掏出稿纸算题，语文课代表开始背诗，指令相同但动作不同。
🔓 开闭原则 (OCP)
对扩展开放，对修改关闭。如果你不理解，你就理解为：「智能手机装新 App」——想要新功能直接下载新应用，绝不需要用螺丝刀拆开手机主板改线路。
🏭 工厂方法模式 (Factory Method)
把对象的具体创建推迟到子类完成。如果你不理解，你就理解为：「总公司把制造工序外包给专业代工厂」——总公司只下达造车指标，由各分厂自己完成零件装配。

🎉 恭喜完成工厂方法模式的探索！

记住核心心法：“把容易变化的实例化细节推迟到子类工厂中去实现，让核心系统永远面向稳定的抽象契约编程。”
